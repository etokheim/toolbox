The Pinned Columns plugin freezes columns to the left or right edge of the grid—essential for keeping key identifiers or action buttons visible while scrolling through wide datasets. Just set `pinned: 'left'` or `pinned: 'right'` on your column definitions and the plugin handles the rest.

## Installation

```ts
import '@toolbox-web/grid/features/pinned-columns';
```

## Basic Usage

Pin important columns like ID on the left and action buttons on the right. The pinned columns stay fixed while the middle content scrolls horizontally.

## Configuration Options

The plugin has no configuration options. It is activated when columns have `pinned: 'left'` or `pinned: 'right'` set.

## Programmatic API

### Compact action-cell expansion

For an LTR right-pinned utility column, `expandedCellWidth` specifies the active
row's cell width in pixels. The column's normal `width` reserves only its persistent
controls. Mouse hover or focus within a row expands its actual cell inward, without
widening its header, other rows, the column track or the horizontal scroll extent.

```ts
{
  field: '__actions',
  utility: true,
  pinned: 'right',
  width: 88,
  expandedCellWidth: 240,
  renderer: renderActions,
}
```

Keep secondary and persistent controls in one inline renderer strip, persistent
controls at the right. No separate floating container or overflow override is needed.
The plugin does not move, clone or remount renderer children. Expansion is clamped
to the visible scroll area and the opposite pinned rail, never below normal width.
A right-pinned chooser after the action column keeps its offset. A pinned neighbour
on the action cell's inner side leaves no room to expand over it.

Focus takes precedence over hover. Retain a surface while a menu has portal focus:

```ts
// Acquire when the menu opens; release when it closes or its component unmounts.
const release = grid.getPluginByName('pinnedColumns')
  .retainCellExpansion(occurrenceId, '__actions');
release();
```

Use the same unique **occurrence ID** as `getRowId`, not a view index or shared
business entity ID. Acquisition throws if there is no unique mounted eligible
cell. The release is idempotent and cannot affect successor ownership. Stable
renderer updates preserve the lease; replacement, recycling, removal, unpinning,
option removal or plugin detach revoke it. A retained menu takes precedence over
hover and row focus. Register an external focus container separately if the menu
also needs the grid-wide external-focus contract.

An unchanged React utility `GridColumn` can retain its attached view and lease
while unrelated column callbacks change. Action declaration/callback, occurrence,
visible field order and primitive/callback options must stay unchanged; nested
option objects/arrays disable retention. Action config changes still retire it.
Raw DOM renderers are not converted into persistent views. See
[mixed native/JSX columns](/grid/react/getting-started/#mixed-native-and-jsx-columns).

#### Styling the active surface

The actual action cell exposes `data-tbw-cell-expanded` as a supported, read-only
**presence attribute**. It follows native menu-lease, focus and hover arbitration,
so use it rather than duplicating that state with `:hover` or `:focus-within`.

Unleased hover follows the same geometric row as `[data-tbw-hovered]`, including
stationary-pointer scrolling. Pointer leave, overlays and touch clear that hover
input without revoking retained menu leases or overriding row focus.

```css
tbw-grid .cell[data-field='__actions'] .row-action-secondary {
  visibility: hidden;
}
tbw-grid .cell[data-field='__actions'][data-tbw-cell-expanded] .row-action-secondary {
  visibility: visible;
}
```

Apply your `row-action-secondary` class only to secondary inline controls.
Persistent controls, especially More, must remain visible and operable.
`visibility: hidden` preserves the inline strip's layout without invisible tab stops.
The marker stays present while a menu lease wins arbitration, even with focus in
a portal. Inactive/ineligible cells and decorative sticky clones do not carry it;
retired ownership removes it before reuse. Presence means active expansion intent,
not that every action fits or that the width exceeds its normal size after clamping.
Select by presence, never by a specific value, and do not mutate the attribute.
Internal width variables are not a supported styling API.

**Scope:** LTR `right` or `end` pins only; effective/inherited RTL is diagnosed
once per controller lifetime and disables expansion and retention. The option does
not fix pre-existing RTL pinning geometry. Call `await grid.forceLayout()` after a
direction change to reconcile ownership. Width must be finite and positive.
Per-row expanded widths, non-pinned cells and editor expansion are not supported.

## Accessibility

Keyboard focus also expands the cell
([SC 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)).
Keep an always-operable, visible menu button among the persistent controls and
expose all secondary actions there. Touch and narrow/clamped layouts must not
depend on hover or invisible tab stops. The plugin does not intercept native
activation or change tab order; the renderer owns button labels, menu semantics,
focus return and target sizes. Hold the menu lease until it closes.

## Pinning Methods

See [`PinnedColumnsPlugin`](./classes/pinnedcolumnsplugin/) for the full list of methods.

```ts
const plugin = grid.getPluginByName('pinnedColumns');

// Get currently pinned columns
const leftPinned = plugin.getLeftPinnedColumns();
const rightPinned = plugin.getRightPinnedColumns();

// Clear all sticky positions
plugin.clearStickyPositions();

// Recalculate offsets (e.g., after column resize)
plugin.refreshStickyOffsets();
```

:::note
To pin or unpin columns at runtime, update the column's `pinned` property in your `gridConfig.columns` and re-assign the config. The plugin reads `pinned` from column definitions during each render cycle.
:::

### RTL Support

For direction-independent pinning, use logical values `'start'` and `'end'` instead of `'left'`/`'right'`:

```ts
{ field: 'id', pinned: 'start' }  // Left in LTR, Right in RTL
{ field: 'actions', pinned: 'end' } // Right in LTR, Left in RTL
```

## Column Reordering Behaviour

When a column is pinned (either via config or the context menu), the plugin **automatically
reorders** it to the appropriate edge of the grid:

- `pinned: 'left'` → moved to the leftmost position (after other left-pinned columns)
- `pinned: 'right'` → moved to the rightmost position (before other right-pinned columns)

When a column is unpinned via the context menu, it is restored to its **original position**
in the column order.

This ensures pinned columns are always visible at the grid edges without requiring the user
to scroll.

## Known Limitations

- **Column Groups support**: Pinned columns work with the
  [Column Groups plugin](../grouping-columns/). When a pinned column belongs to a
  column group, the group header is automatically split so the pinned portion stays
  sticky while the rest scrolls normally. For explicit (named) groups, the group label
  scrolls with the non-pinned fragment until it reaches the pinned edge, then transfers
  to the pinned fragment.

- **Header-only sticky in virtualized grids**: Due to the row virtualization architecture
  (`will-change: transform` on the rows container), `position: sticky` only works on
  **header cells**. Data row cells receive the sticky CSS classes but the browser cannot
  honour them because the transformed ancestor creates a new containing block.

The Undo/Redo plugin tracks all cell edits and lets users revert or replay changes with familiar keyboard shortcuts (Ctrl+Z / Ctrl+Y). It maintains an in-memory history stack with configurable depth—perfect for data entry workflows where mistakes happen.

> ⚠️ **Required Dependency:** This plugin requires [EditingPlugin](/grid/plugins/editing/) to be loaded first. UndoRedo tracks the edit history that EditingPlugin creates.

## Installation

```ts
import '@toolbox-web/grid/features/editing';
import '@toolbox-web/grid/features/undo-redo';
```

## Basic Usage

Enable both features and history tracking is automatic—every cell edit is recorded, and users can navigate back and forth through the edit history.

## Programmatic API

### Row identity and unavailable edits

History records the edited row's existing ID (`getRowId`, or `id`/`_id`) and field
name, rather than replaying against its old view position. Unique IDs follow
immutable row replacements; filtered-out source rows remain updatable. Rows
without IDs retain history only for the original object while it remains in the
source or processed rows.

Removed, unresolved or ambiguous targets produce a `TBW041` warning and are
skipped; other edits in a compound action still apply. The action moves between
the stacks normally, even if some edits were skipped. Replacing the `getRowId`
function also invalidates previously recorded targets. History does not recreate
removed rows, and grouping edits into one undo step does not make them atomic.
Queued row replacements temporarily make targets unavailable until
processing settles, rather than allowing replay through a superseded view.

For manual `recordEdit(rowIndex, ...)`, pass the current processed-view index at
recording time. An action's exposed `rowIndex` remains its original coordinate;
replay and focus use its recorded owner and field.

```ts
const plugin = grid.getPluginByName('undoRedo');

plugin.undo();
plugin.redo();
const canUndo = plugin.canUndo();
const canRedo = plugin.canRedo();
plugin.clearHistory();
```

After an undo or redo, focus moves to the restored cell once the grid has re-rendered, so it lands
on the row's new position after any re-sort or re-filter. If the row is filtered out, focus stays
where it was. Deleted targets are skipped without moving focus; stacks still advance.

### Preserving history across remounts

```ts
import type { UndoRedoSnapshot } from '@toolbox-web/grid/plugins/undo-redo';

// Before removing or reconfiguring the source grid:
const snapshot: UndoRedoSnapshot = grid.getPluginByName('undoRedo').captureHistory();

// After installing the destination's rows/config, with the same getRowId function:
await replacementGrid.ready();
replacementGrid.getPluginByName('undoRedo').restoreHistory(snapshot);
```

The opaque token preserves both stacks and their original captured owners,
resolver references and ambiguity evidence. Replay retains the safeguards above;
restore never reinterprets IDs using the destination's current resolver. Use it
only for the same logical dataset. ID-less edits require the original live row
objects; a unique ID can follow an immutable replacement.

Snapshots survive source cleanup and can be restored repeatedly. Action containers
and compound children are copied at capture and each restore; row objects,
resolvers and old/new cell values remain references, not deep copies. Release
the token when no longer needed to allow those references to be collected.
The token does not directly store a source grid/plugin reference, but retained
row, resolver or value references can indirectly retain them.

Only the originating loaded UndoRedo module accepts the token. JSON, structured
clones, workers, different package instances and persistent storage are unsupported.
Stack getters are for inspection, not serialization or restoration.

Restore replaces both stacks without changing rows, dirty baselines, editors or
open transactions. Detach still clears live history: capture **before** detach,
then restore **after** the destination is ready. Both methods reject detached
plugins, open transactions, replay and synchronous `history-change` listener
reentry with `TBW003`. Invalid tokens and snapshots exceeding the destination's
`maxHistorySize` are also rejected before replacement; undo+redo top-level entries
count together, with each compound counting as one. Nothing is silently trimmed.

A successful restore clears pending history focus and emits one `history-change`,
including for empty history. It emits no `undo`, `redo` or `cell-change`, writes
no rows and requests no focus. History mutators are rejected during its synchronous
notification; schedule follow-up operations after restore returns.

### Compound Actions (Transactions)

When a user edit cascades programmatic changes to other fields, group them into
a single undo step so Ctrl+Z reverts everything at once:

```ts
grid.on('cell-commit', ({ row, rowId, rowIndex }) => {
  const undoRedo = grid.getPluginByName('undoRedo');
  undoRedo.beginTransaction();

  // Record cascaded updates manually (pass rowId so off-screen rows are targeted correctly)
  const oldTotal = row.total;
  undoRedo.recordEdit(rowIndex, 'total', oldTotal, newTotal, rowId);
  grid.updateRow(rowId, { total: newTotal });

  // End after the auto-recorded original edit is captured
  queueMicrotask(() => undoRedo.endTransaction());
});
```

| Method              | Description                                         |
| ------------------- | --------------------------------------------------- |
| `beginTransaction()`| Start buffering edits into a compound group         |
| `endTransaction()`  | Finalize and push the compound as a single undo step|
| `recordEdit()`      | Manually record a cell edit (buffered during txn)   |

### undo / redo

Fired when an action moves between history stacks, whether it came from the keyboard
or from `plugin.undo()` / `plugin.redo()`. Targets can be skipped, so these events
are not proof of data mutation. For ID-based replay, synchronize external row state
from accepted `cell-change` events with `source: 'history'`, not by replaying the
action yourself.

```ts
grid.on('undo', ({ action, type }) => {
  // `action` is a single 'cell-edit' or a 'compound' group (see Compound Actions above)
  if (action.type === 'cell-edit') {
    console.log(`${type}: reverted ${action.field} on row ${action.rowId ?? action.rowIndex}`);
  }
});

grid.on('redo', ({ action, type }) => {
  if (action.type === 'cell-edit') {
    console.log(`${type}: reapplied ${action.field} on row ${action.rowId ?? action.rowIndex}`);
  }
});
```

See [`UndoRedoDetail`](./interfaces/undoredodetail/) for the full event payload type.

### history-change

Fired whenever the history changes: an edit is recorded outside a transaction, a non-empty
transaction ends, an undo or redo runs, `restoreHistory()` succeeds, or `clearHistory()` empties a non-empty history. Bind your
toolbar buttons to it:

```ts
grid.on('history-change', ({ canUndo, canRedo }) => {
  undoButton.disabled = !canUndo;
  redoButton.disabled = !canRedo;
});
```

See [`HistoryChangeDetail`](./interfaces/historychangedetail/) for the payload type. In the
framework adapters, `onHistoryChange` (React), `@history-change` (Vue) and `(historyChange)`
(Angular) expose the same event; `useGridUndoRedo()` / `injectGridUndoRedo()` already refresh
`canUndo()` / `canRedo()` from it.
